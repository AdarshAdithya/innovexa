# Clinical Trial Eligibility Screener

A single-agent AI system that screens synthetic patients against multiple clinical trials. For every
patient–trial pair it returns **ELIGIBLE / NOT_ELIGIBLE / NEEDS_REVIEW**, a per-criterion breakdown,
a rationale that cites protocol sections, and a confidence score. A React UI streams the agent's
reasoning live.

**Core design principle: the LLM reads and writes language, the rule engine makes the decision.**
Every verdict traces back to a specific rule and a specific patient value.

> All data is synthetic, generated by `backend/data/generate.py`. This is a hackathon prototype,
> not a medical device, and must not be used for real enrolment decisions.

---

## Quick start

```bash
# backend
cd backend
python -m venv ../.venv && source ../.venv/bin/activate
pip install -r requirements.txt
cp .env.example .env              # add LLM_BASE_URL / LLM_MODEL for the event model, or leave empty
python data/generate.py           # writes trials.json, patients.json, labels.json
uvicorn app.main:app --reload     # http://localhost:8000  (docs at /docs)
pytest -q                         # 55 tests

# frontend (second terminal)
cd frontend
npm install
npm run dev                       # http://localhost:5173
```

With no LLM configured, everything still runs in **offline mode**: a deterministic criteria parser,
a negation- and time-aware note reader, template rationales and a rubric judge. Set `LLM_BASE_URL`
and `LLM_MODEL` to any OpenAI-compatible endpoint and the same code paths switch to the model. Only
`app/llm.py` needs changing for a different client.

## Architecture

```
React (Vite, Tailwind, Recharts)
  Dashboard · Screening + live agent trace · Patient drawer · Grid · Accuracy · Ask · Cohorts · Review
        │  REST + Server-Sent Events
FastAPI  (CORS allow-list, rate limit, optional API key, security headers, audit log)
        │
Screening agent  ── plan → tools → self-verify → escalate to human
        │
Tools:  criteria parser · rule engine · note reader · explainer · RAG retriever
        judge · anomaly detector · cohort clustering · trial ranker · NL query
        │
SQLite (trials, patients, rule cache, verdicts, reviews, audit log) · TF-IDF / ChromaDB index · LLM
```

| File | Role |
|---|---|
| `app/parser.py` | Criteria text → JSON rules. LLM output validated with Pydantic, retried once with the error, cached in SQLite by criteria hash. Deterministic parser as fallback. |
| `app/rules.py` | Rule engine. No LLM. MET / NOT_MET / UNKNOWN, unit normalisation (mmol/L→mg/dL, lb→kg, mmol/mol→%), plausibility ranges, nested `any_of`, decision logic, confidence, counterfactuals. |
| `app/notes.py` | Offline note reader: negation ("no history of"), time windows ("3 years ago" vs "within 6 months"), structured-vs-note contradiction detection. |
| `app/explainer.py` | Note-based criteria (LLM or note reader) and rationales. A rationale that contradicts the decision is rejected and regenerated. |
| `app/agent.py` | LangChain tool-calling loop (or a fixed plan offline) that streams every step, then re-checks its decision against the rule engine. |
| `app/rag.py` | Protocol chunked by criterion; retrieval gives the `[Inclusion 3]` citations. TF-IDF by default, ChromaDB with `RAG_BACKEND=chroma`. |
| `app/ml.py` | Isolation Forest, K-Means cohorts, trial ranking. |
| `app/judge.py` | LLM-as-judge for explanation clarity (1–5), rubric fallback. |
| `app/query.py` | Natural-language cohort questions → a validated filter over saved verdicts. |
| `app/evaluate.py` | Accuracy, precision, recall, confusion matrix, mismatches, clarity, pure-LLM baseline. |
| `app/security.py` | PHI redaction, prompt-injection guard, rate limiting, security headers. |

### Decision logic (in order)

1. Any exclusion MET → NOT_ELIGIBLE
2. Any inclusion NOT_MET → NOT_ELIGIBLE
3. Any criterion UNKNOWN → NEEDS_REVIEW
4. Otherwise ELIGIBLE

Confidence is the share of criteria with a known status. Missing data, an implausible value, a
contradiction between the note and a structured field, or a suspected prompt injection all produce
UNKNOWN, never a guess.

## How the AI parts work

- **Agentic.** The agent receives four tools (`get_criteria`, `evaluate_structured_rules`,
  `check_note_criteria`, `submit_decision`) and decides the order. After it submits, a
  self-verification step re-runs `decide()` on the evidence. If the agent skipped a tool, left a
  note criterion pending, or proposed the wrong decision, the step is corrected and logged as a
  `correction` event. NEEDS_REVIEW cases are escalated to the human review queue. If the model
  cannot do tool calls, the agent falls back to a fixed plan that calls the same tools.
- **Generative AI.** Criteria parsing, note reading, rationales, LLM-as-judge clarity scoring,
  natural-language cohort chat, RAG citations, counterfactuals ("Would be eligible if eGFR ≥ 45"),
  and a **pure-LLM baseline** (Accuracy page → *Compare with pure-LLM baseline*) that screens every
  pair with a single prompt and no rule engine. That baseline is the "second approach" to show the jury.
- **Machine learning.** See the next section.

## ML design decisions (verified, not just added)

| Method | Used for | Decision |
|---|---|---|
| Physiological range check | HbA1c 45 %, eGFR 0, etc. | **Changes the verdict.** The value becomes UNKNOWN, so the case goes to review unless another rule already excludes it. Deterministic and explainable. |
| Isolation Forest | Multivariate outliers on age + 6 labs (standardised, median-imputed, `contamination=0.07`) | **Advisory only.** With 30 patients it also flags legitimate boundary patients (e.g. P002 with BMI exactly 40), so letting it force NEEDS_REVIEW would cost accuracy for no safety gain. Each flag carries a z-score reason. |
| K-Means | Cohort scatter (PCA to 2D), `k` picked by silhouette over 2–4 | Descriptive only. Silhouette is about 0.29 on 30 patients: weak structure, stated in the UI. Implausible records are excluded from fitting. |
| TF-IDF similarity + verdict | "Best-matching trials" per patient | 70 % rule-based verdict, 30 % text similarity, so an eligible trial always outranks a merely similar one. |
| Logistic regression calibration | — | **Not built.** With 120 labelled pairs and near-perfect rule accuracy there is almost no negative class to calibrate on. Rule-coverage confidence is deterministic and easier to defend. |
| SHAP | — | **Not used.** The rule engine already gives exact per-criterion attribution; SHAP on an Isolation Forest is approximate, slow and one more dependency. The z-score reasons cover anomaly explanation. |

## Data security

Even with synthetic data, the app is built as if the data were real:

- **Secrets.** `.env` is git-ignored from the first commit; only `.env.example` is tracked.
- **PHI minimisation.** Notes are passed through `redact_phi()` (names, MRNs, phone numbers, emails, DOBs) before any LLM call.
- **Prompt injection.** Patient notes and protocol text are wrapped in `<untrusted>` tags with a system guard. A note that looks like an injection ("ignore previous instructions…") is never used to decide a note-based criterion; the criterion becomes UNKNOWN and goes to human review. Even if an injection slipped through, the model can only move a note criterion; every structured criterion is decided by the rule engine.
- **The LLM never controls execution.** LLM output is parsed as JSON and validated against Pydantic schemas with fixed field and operator allow-lists. The NL chat produces a filter over saved verdicts, never SQL. Nothing is `eval`'d.
- **Input validation.** Pydantic constraints on IDs (`^[A-Za-z0-9_-]+$`), ages, lengths and enums; malformed records are rejected with a 422.
- **Transport and API.** CORS allow-list (not `*`), per-client rate limiting, optional `X-API-Key`, `nosniff` / `DENY` / `no-store` headers.
- **Audit log.** Every screen, query, new trial and human review is logged with identifiers only, never note text or lab values (`GET /audit`).
- **Local data.** SQLite and Chroma files are git-ignored.

## Accuracy

`GET /metrics` screens all 30 patients against all 4 trials (120 labelled pairs) and compares with
`backend/data/labels.json`.

**Offline mode: 120 / 120 (100 %), eligible precision and recall 100 %.** Read this with care:

- 102 of the 120 pairs are NOT_ELIGIBLE (most patients don't have a given trial's condition), so
  the per-class numbers and the 5 NEEDS_REVIEW cases matter more than the headline.
- The deterministic parser was written against these four protocols' phrasing. The fair test is
  the event model on a protocol it hasn't seen: upload one on the Dashboard, then re-run the evaluation.
- Labels are computed from each patient's *true* state by separate functions in `generate.py` that
  share no code with the parser or rule engine, and the edge cases were checked by hand.

Edge cases in the data: boundary ages (18, 40, 75) and labs (HbA1c 7.0 / 10.5, eGFR 45, SBP 140,
BMI 40.0), missing HbA1c and eGFR, glucose in mmol/L, weight in lb, "no history of MI", MI 3 months
vs 3 years ago, a note that contradicts the pregnancy field, HbA1c 45 %, nested "(T2D or HTN)",
undocumented dialysis status.

## Tests

`pytest -q` runs 55 tests: every operator, boundaries, missing values, unit conversion, every
branch of `decide()`, negation, time windows, contradictions, nested logic, an empty trial,
malformed records, prompt injection, PHI redaction, parser cache, unseen phrasing, the LLM paths
with a stubbed model (validation retry, fallback, a contradicting rationale being rejected), and
the API including the SSE stream.

**Failure found and fixed:** "BMI no more than 35 kg/m2" parsed as `bmi > 35`. The pattern for
"more than" matched before "no more than". Fixed by checking the negated comparators first
(`parser._comparisons`); covered by `test_unseen_phrasing_parses`.

## Demo script (about 3 minutes)

1. The problem in one line, then the architecture above.
2. **Screening** → *Run agent (live trace)* on T1-DIAB and watch the plan, tool calls, verification and escalations stream.
3. Click **P007**: the pregnancy contradiction, cited sections and confidence. Click **P004**: glucose 16 mmol/L = 288 mg/dL and the counterfactual.
4. **Dashboard** → data-quality flags: P006 HbA1c 45 % (implausible, changes the verdict) vs Isolation Forest advisory outliers.
5. **Ask** → "Which patients over 60 are eligible for the diabetes trial?"
6. **Accuracy** → confusion matrix, clarity score, and the pure-LLM baseline if the model is connected.
7. `docs/spec.md`, `docs/tasks.md`, `docs/prompts.md`, and the team's own decision (see the end of `docs/prompts.md`: the Isolation Forest is advisory and never overrides the rules).

## Fallbacks

- Slow model: parsed rules are cached; verdicts are saved in SQLite; *Fast pipeline* skips the agent loop.
- Agent loop breaks: it switches itself to the fixed plan with the same tools (logged as a correction).
- No model at all: offline mode runs every feature.
